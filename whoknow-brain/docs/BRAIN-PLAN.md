## 一、一句话定位

**大脑 = 胡闹宇宙的自动段子工厂 + 强管理平台 + 自我进化知识库。**

它不上台表演（不像 waimai/mart 那样直接给用户玩），而是在后台给所有 app 供"内容弹药"——段子、剧本、活动。

---

## 二、核心闭环（6 步）

| 步 | 做什么 | 说明 |
|---|---|---|
| 1 每天自动 | 抓新闻（复用 OpenClaw 信源治理）→ 学优秀段子 → 归纳公式 → 套公式+知识库+新闻+节假日天气 = 产新段子 | 全自动，MVP 前期人工协助调试 |
| 2 加工 | 通用底料 + 各 app 调料 → 合规审计（高危人工审）→ 成品段子库部署 Vercel | 一处写、两处受益 |
| 3 分发 | 各 app 拉去跑 | app 跑"上次成功部署的数据" |
| 4 你管 | 管理平台：看段子 / 发布 / 调权重 / 管新闻渠道，高危拍板 | 轻量后台，你只看结果和拍高危 |
| 5 进化 | app 用户匿名反馈 → 回传 → 加权 → 公式和权重自我进化 | 用时间堆积，不持个人数据 |
| 6 兜底 | 更新失败用旧版 / 挂了不影响已部署 app / 知识产权留本地不出 | 安全网 |

## 三、已拍板决策清单（闭合项，勿再议）

**内容生产**
- 终态全自动产内容；MVP 前期用户协助调试，后期全自动。
- 公式 = 套路框架 + 参数槽（如「[人物]在[场景]干[离谱事]」）；AI 全自动归纳。
- 公式质量靠"只审最终段子 + 反馈加权淘汰烂公式"，不孤立审公式。

**发布与风险**
- 5 级风险分级：前 3 级自动发，后 2 级高危人工审；渐进放权（后期自动发越来越多）。
- 通用底料 + 各 app 调料：中枢一处写、两处受益。
- 部署即版本：更新失败，app 继续用上次成功数据。
- 带生效时间的活动剧本全宇宙同步；高危需人工审。
- 版本备份 + 一键回退（用 Vercel 部署回退更合适）。

**知识与发展**
- 每日学习 + 反馈加权自我进化（时间堆积）；大脑是"数据加工中心"。
- 知识库每日扩充；多渠道新闻挖掘（时事/热点/财经/科技）作素材。
- 反馈回传 = 匿名聚合统计，不持玩家个人数据。
- 加工数据（知识产权）存本地、不出服务器；app 只收成品段子库，不收知识库。

**平台与边界**
- 管理平台 MVP = 最小可用（看段子 / 发布 / 反馈）；完整控制后期加。
- 新闻渠道 MVP = RSS + 免费 API。
- 成品上云 = 本地加工 → 成品段子库部署 Vercel → app 拉取。
- 边界：非永远在线 / 不持玩家个人数据 / 挂了不影响已部署 app。
- 新闻合规：新闻衍生段子归高危后 2 级，必人工审。

**花钱原则（07-29 深夜修正）**
- 前期能省则省（轻量 cron / 免费额度内 / 轻量后台），不为冗余架构提前付费。
- 后期若任务重到简单 cron 调度扛不住，**该买常驻服务器就买**——大脑是宇宙核心、值得。
- 判据：是否"冤枉钱"，而非是否"花钱"。

**参考基线（OpenClaw 新闻工作流 v1.0）**
- 直接复用其"信源候选/观察/正式三级池 + 5 维健康分自动升降级 + 多 cron 失败隔离"范式。
- 须改造：①输出从"推人看早报"改为"喂公式生段子"；②增"合规性"评分维度（涉政/涉敏降权或黑名单）；③源类型扩到泛娱乐梗源（段子手/沙雕新闻/搞笑博主）；④它是上游中转站，非终点。

## 五、未闭合细节（余 2 项待定）

> ⑥①③②已闭合（②=暂选A+审核台富信息强约束+升级留待讨论）；**RAG 定为后期计划（规模触发，含多触发条件 + 提醒机制）**；④⑤留 Phase 3 细化。

**① 公式怎么存和管（已拍板 · 2026-07-29）**
- 问题：公式=框架+参数槽，系统在哪落地？什么文件格式？怎么版本化（新不覆盖旧）？AI 新公式怎么不跟旧打架？怎么回退？
- 拍板结论：选 **A（每条公式独立记录）融合 D 可解释性**。
  - 公式库 = 一堆独立单元（文件或记录），每条带：**唯一 ID + 版本号 + 创建时间 + 效果评分（来自反馈） + 状态（启用/淘汰/归档）**。
  - **AI 只新增、不删改旧**：要改 = 出新版本；淘汰 = 评分过低+标记，不物理删（归档留底备查）。
  - 融 D：每条公式附带它的**来源模范段子 + 生成样例**，形成可解释单元，便于审计追溯（直接服务"高危人工审"与"反馈加权淘汰"）。
- 理由：独立记录+版本化完美支持"只增不删改、回退、归档"，对接资产安全与合规审计；避开 B 单文件大表的并发冲突/误改脆点；C（SQLite）前期过重（花钱原则=前期省，可后期上）；D 可解释性让审计看得懂。

**② 人工审实操（已拍板 · 2026-07-29）**
- 问题：后 2 级高危谁审、在哪审、你不在时怎么办、审不过已部署的怎么处理？
- 拍板结论：**暂选 A（管理平台审核台），升级路径留待后续讨论。**
  - **MVP = A**：高危段子自动进"待审队列"，你在管理平台审核台点"通过/驳回"；**你不在时队列堆积、绝不自动发**（安全优先）；驳回标记作废、移出候选、永不部署。
  - **升级位（未定，到时再讨论）**：B（手机/IM 推送审核）、C（授权他人代审）、D（混合分级：审核台+代审+最高级需你终拍）。届时按需叠加，**架构预留扩展**（审核台可加"代审人"字段，不改动底层）。
  - **发布后撤回**：属"发布后治理"，建议**留能力位、MVP 不实现**（合规审计闭环一部分），具体留 Phase 3 定。
- **审核台信息密度要求（用户强约束）**：审核台**不能只显示段子本身**，必须一并呈现"辅助一眼判断"的信息，避免你四处找资料、翻记录。主理人据此建议审核台至少聚合：
  1. **风险标注**：命中哪几条风险规则、风险等级、为何被归后 2 级（涉敏词 / 衍生自哪条新闻 / 哪类源）。
  2. **来源链路**：由哪条新闻/知识库文章触发、套了哪个公式、用了哪些素材（可展开溯源）。
  3. **合规扫描**：自动跑过的合规/敏感词扫描结果摘要。
  4. **同类历史**：同类段子过往通过/驳回记录、匿名聚合的用户反馈表现。
  5. **一键上下文**：相关 app 当前剧本/活动背景，便于判断"这条放出去合不合适"。
  - 目标：你打开审核台，**扫一眼即知"问题在哪、风险多高、该不该放"**，无需跨系统查证。

**③ 知识库生命周期 + 权重升降机制（已拍板 · 2026-07-29）**
- 问题：每天灌新闻+学段子，只增不减？本地存储会不会爆？要不要清理/归档？权重怎么管？
- 拍板结论：**选 A（热/温/冷分层 + 归档不删）融合"权重 + 类新闻源升降机制"**。
  - **分层**：知识库按"新鲜度 + 命中率"分热/温/冷三层；冷层自动**归档**（挪便宜存储/压缩，**不物理删**），可配置保留期（如热30天/温180天/冷归档转存）。
  - **权重 + 升降机制（用户补强）**：除冷热外，每篇文章带**权重分**；定期（定时任务）对全库文章**重新打分、自动升降层**（同构 OpenClaw 新闻源"候选/观察/正式池 + 5维健康分自动升降级"）。低权重/长期不命中者降冷归档，高权重/高频命中者升热。
  - 不物理删，契合"知识产权留本地、不丢资产"底线，也保住公式归纳所需历史样本。
  - **打分维度（已拍板 · 2026-07-29）**：每篇文章权重分 = **复用 OpenClaw 新闻源 5 维（命中率 / 时效性 / 相关性 / 权威性 / 稳定性）+ 大脑特有 1 维「梗性 / 趣味性」**。前 5 维同构已验证范式、零试错；「梗性」补段子产出必需的"够好笑够能胡闹"信号，避免滤出"权威但不好笑"的料。
- 理由：分层+归档让热数据快、冷数据便宜，前期本地/免费额度扛更久，延迟"该买服务器"触发点；权重升降复用已验证的新闻源治理范式，零试错成本；可配置保留期让你后期调参控成本不改架构。

**③-附 · RAG 检索（已闭合 · 后期计划，规模触发）**
- **结论**：RAG **不纳入 MVP / 前期架构**。前期知识库小，用"权重+冷热层"作简单过滤器挑 Top-N 整批塞 prompt 即可。**RAG 列入后期计划，由客观条件触发构建。**
- **原讨论要点（已消化）**：
  - 纯 RAG 按语义相似度，本身判不了业务权重；权重由升降机制写入元数据，检索时作二次排序/过滤（"RAG 找得准，权重排得对"）。
  - 触发判断可自动化：纳入大脑"每日自我进化"cron 做"检索健康度监控"，检测全自动；激活（花钱/起服务）早期通知用户、后期预算内渐进放权自动开。
- **启动时机 · 触发 RAG 构建的客观条件（任一达成即触发）**：
  1. **体量**：知识库文章数 ≥ ~1万条（或总素材 token 量达预设上限）。
  2. **上下文溢出**：单次生成所需素材 token 数 ≥ 模型上下文窗口 ~30–40%（或频繁触发截断/摘要丢失）。
  3. **成本**：单次生成平均 token 成本 ≥ 预设阈值（或远超"上 RAG 后预估成本"）。
  4. **延迟**：p95 生成延迟 ≥ 预设阈值（因 prompt 过大）。
  5. **相关性质量**：素材采用率 < ~30%（喂入素材真正被用上的比例），或 AI 裁判相关度分 < 阈值，持续 ≥ N 天。
  6. **人工干预率**：因"捞偏/不对症"导致用户驳回/重改段子比例显著升高（反馈信号）。
  7. **多主题并发**：同时服务的 app / 活动主题数增多，全局权重过滤无法兼顾多主题精准度。
- **提醒机制（铁律）**：上述条件由"检索健康度监控"每日自动量。自本决策起，**主理人在后续任何开发新功能 / 更新维护时，若监测到任一触发条件已达成，必须主动提醒用户："RAG 触发条件已满足，需启动 RAG 构建"**，不待用户问。
- **遗留细化（留 Phase 3 实际引入时）**：权重如何进检索（先过滤 or 重排）、冷层能否被 RAG 搜到——由 engineering-lead 出检索架构 ADR 时定。

**④ 反馈回传通道【待定】**
- 问题：app 在 Vercel、大脑在本地/服务器，匿名反馈跨环境怎么回传？大脑非永远在线，通道怎么稳？
- 我的倾向：app 端攒本地匿名聚合，定时批量上报大脑侧轻量接收端；大脑不在线时排队。

**⑤ 大脑↔app 数据契约【待定】**
- 问题：成品段子库长啥样、app 怎么拉、版本怎么对、降级怎么触发？
- 我的倾向：固定 JSON schema + 版本号 + 校验和，app 按版本拉，校验失败用上一版。属接口细节，Phase 3 定。

**⑥ 拆解归纳公式机制（已拍板 · 2026-07-29）**
- 问题：AI 全自动归纳，具体怎么从优秀段子提炼出公式？
- 拍板结论：初期走 A 种子法（用户人工精选"模范段子"做种子 → LLM 归纳初始公式库），随公式库与反馈数据积累，**逐步转向 B 纯 LLM 自归纳**（海量段子/新闻喂 LLM 自行总结，减少人工种子依赖）。
  - **A→B 切换判据（已拍板 · 2026-07-29）**：双指标门槛——①**公式库规模 ≥ 200 条**（种子+早期迭代攒够多样性）；②**匿名反馈样本 ≥ 1000 条**（证明评分机制已可信）。**过渡期 A/B 并行**：B 提的建议公式先走"试用/审核通道"验证，跑稳再完全放手。N/M 为初值（200/1000），后续按真实运行数据再调。
- 理由：A 保首版质量底线，B 实现规模化与低人工；A→B 渐进，规避纯 B 起步跑偏风险。完全符合"公式由 AI 全自动归纳"总原则（人不写公式，仅初期挑种子）。

**⑦ 调料责任归属 · 通用底料+各 app 风格化（已拍板 · 2026-07-29）**
- 问题：各 app 的"风格化调料"（腔调/语气/梗风格）由谁写、谁套？
- 拍板结论：**选 A（大脑统一产多版本 + 派发），app 端零加工、纯拉取。**
  - 大脑套用各 app 的"风格模板"产出各 app 专属段子库，直接派发；app 仅拉取已部署成品，不做风格化加工。
  - **风格模板维护（已拍板）**：初期由你（产品主理人）在管理平台配种子模板；后期 AI 从各 app 现有内容自动学腔调、迭代优化（同公式 A→B 渐进逻辑）。
  - **升级位（架构预留）**：若某 app 腔调迭代极快想自主，后期可叠加 B 类"app 端风格化适配层"，不改动中枢派发模式。
- 理由：对齐已拍板"app 只收成品段子库、不收知识库"；契合"大脑中枢 + app 轻前端"，大脑挂了 app 照跑；风格模板集中大脑，改腔调一处生效全宇宙一致。B 让 app 变重、C 增接口、D 削弱中枢，均不如 A。

## 七、已知风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| 合规风险 | 自动抓真新闻+套公式，易产高危内容 | ②审核台富信息（风险标注+来源链路+合规扫描+同类历史+上下文）一眼判风险；后 2 级必人工审；信源增合规维度 |
| 存储风险 | 知识库日增，前期本地或爆 | ③热温冷分层归档+权重升降机制；冷层不进热检索库；触发"该买服务器"评估 |
