## 1. 内容生产流水线设计评估（拆解 → 组装 → 派发）

### 1.1 三段逻辑自洽性

| 段 | BRAIN-PLAN 描述 | 自洽性 | 断点 / 备注 |
|---|---|---|---|
| **拆解** | 每日抓新闻→学优秀段子→归纳公式（⑥ A→B） | 🟢 逻辑闭环 | 公式=框架+参数槽，归纳判据（≥200 条 + ≥1000 反馈）已闭合（⑧.1 标"前置已满足"） |
| **组装** | 通用底料 + 各 app 调料 → 合规审计 → 成品库部署 | 🟡 基本自洽 | "通用底料"的具体内容未定义；合规审计依赖②审核台（实现前置未齐，见 §3）；部署=Vercel 版本回退已对齐 api-spec 分发层 |
| **派发** | app 拉"上次成功部署的数据" | 🟢 自洽 | 与 api-spec "配置分发层 + 版本号 + ETag"一致；app 零加工、纯拉取，对齐"大脑挂了 app 照跑" |

**结论**：三段主线自洽，**最大断点在"组装"段的合规审计依赖未建组件**（风险规则库/合规引擎/审核台），且"通用底料"是黑盒。这不是逻辑断裂，是"实现前置未闭合"——与三司会审焦点①一致。

### 1.2 公式 A→B 渐进，能否保住段子质量根基？

**能，但有个前提没写清**。A（人挑种子）→ B（纯 LLM 自归纳）的切换判据（200/1000 双门槛 + 过渡期 A/B 并行验证）设计合理，规避了纯 B 起步跑偏。**但质量根基的真正守门员不是"公式怎么归纳"，而是两条**：

1. **只审最终段子 + 反馈加权淘汰烂公式**（③-附已定，方向对）；
2. **公式本身是否 engineered 出"反差喜剧"**——这是 BRAIN-PLAN 的盲区。

> ⚠️ **设计发现 D1（反差喜剧未工程化）**：BRAIN-PLAN 把"真实外壳×胡闹内核=反差喜剧"当成产品铁律喊了，但公式结构（框架+参数槽）是**通用段子生成器**，没有显式把"反差"做成公式的一阶参数。当前设计隐含假设"真实新闻 + 套公式"会自动长出反差，这依赖 LLM 运气而非设计。
> **建议**：公式参数槽应内置"反差轴"——至少含 `现实锚点(realness_anchor)`（来自新闻/节假日/天气的真实元素）+ `胡闹偏移(absurd_offset)`（公式控制的离谱程度）+ 二者落差作为质量信号。这样"反差喜剧"是被设计出来的，不是 LLM 碰巧生成的。

### 1.3 "截图传播"是否在闭环里被度量？

**没有，目前只是愿望**。产品铁律 #1 = "截图即胜利 / 每个交互回答用户会截图吗"。但 BRAIN-PLAN 的质量加权只挂了 `梗性`（趣味）维度，没有"传播力/截图率"作为可度量的反馈维度。三司会审（老子/五行诀）已点出"质量加权应含传播力维度，未明确"，BRAIN-PLAN ⑧.3 P1 也认了"应含传播力/趣味性"。

> ⚠️ **设计发现 D2（截图传播未闭环）**：段子的成功标准是"玩家截图发圈"（4 大痛点滤网：无聊→想笑→没钱也想消费→管不住手）。大脑的**自我进化闭环必须闭合在 app 玩家接收端**，而不是只闭合在主理人审批端。因此④反馈回传不是"豁免的 nice-to-have"，它是**唯一直达 4 痛点滤网的信号**。BRAIN-PLAN ⑧.3 已声明"每日自我进化因④未建而暂停"——这是对的，但我强调：**这意味着 MVP 大脑是一个"静态种子生成器"，不是"自我进化知识库"**，必须显式告知主理人，否则期望错位。
> **建议**：④反馈回传应被提为 **P1（非豁免）**，其回传结构至少含：截图率（代理：段子卡停留时长/分享意图埋点）、replay 率、梗性命中反馈；这些直接喂给③权重的"传播力"维度，使"截图传播"从口号变度量。

## 2. 审核台设计可落地性（富信息 5 要素）

### 2.1 5 要素数据来源映射

| 富信息要素 | 数据从哪来 | 当前基座 | MVP 能否兑现"一眼看穿" |
|---|---|---|---|
| ① 风险标注 | 风险规则库 + 等级判定 | **`禁忌词清单 v1.0` 已存在**（红绿灯分级 + 误杀率10%/漏掉率0.1%） | 🟢 部分可达：禁忌词红线可自动标；但"新闻衍生段子"的**衍生风险归因**（衍生自哪条涉敏新闻）层未建 |
| ② 来源链路 | 拆解-组装溯源（公式ID + 触发新闻/素材ID） | 公式库①已设计"来源模范段子+生成样例" | 🟢 可达：只要公式/素材带 ID 即可展开 |
| ③ 合规扫描 | 合规扫描引擎 | **禁忌词清单 = 合规引擎的"红线子集"基座**，但缺新闻衍生/品牌化名/真实信息泛化的完整扫描 | 🟡 半可达：红线可扫；衍生风险需补规则 |
| ④ 同类历史 | ④反馈回传 + 历史通过/驳回库 | **④豁免未建** → 要素 4 数据为空 | 🔴 MVP 不可达（BRAIN-PLAN ⑧.3 已认"降级为暂无"） |
| ⑤ 一键上下文 | 各 app 当前剧本/活动背景 | api-spec envelope 含 `story_assets`/`ui_meta` | 🟢 可达：从已部署 envelope 读 |

### 2.2 判定：MVP 能否"一眼看穿"？

**部分能，且必须发降级声明**。三司会审对此判 FAIL（MVP 不可全落地），我同意但给更精确的界定：

- **一眼看穿的核心（风险标注 + 来源链路 + 合规扫描红线子集）在 MVP 是可达的**，因为 `禁忌词清单 v1.0` 已经把"风险规则库/合规引擎红线"的基座建好了——BRAIN-PLAN ⑧.1 把"风险规则库/合规引擎（待建）"写死成待建，**低估了已有基座**，应改为"红线基座已具（禁忌词清单），待补衍生风险归因层"。
- **要素 4（同类历史）因④豁免确实空**，必须按 ⑧.3 声明降级；但**降级不能只写"暂无"**，而要给主理人一个"暂无时的替代判据"——例如用"该公式的历史通过率 + 该素材命中红线等级"临时顶替"同类段子反馈表现"。否则主理人面对高危段子，富信息少了一块，反而更易误判。

> 🟡 **设计建议 D3（审核台降级要有替代判据）**：声明 MVP = 段子 + 来源链路 + 基础风险标注（含禁忌词红绿灯等级 + 命中误杀/漏掉风险）+ 上下文；要素 4 以"公式历史通过率 + 素材红线等级"临时顶替，并预埋"发布后撤回能力位"。这比单纯"暂无"更保安全，也呼应⑧.3 P2 的撤回能力位建议。

### 2.3 与总纲里程碑的硬冲突（本评审最关键发现）

> 🔴 **设计发现 D4（阶段映射断层 · 最高优先级阻断项）**：`胡闹宇宙总体设计方案 v3`（2026-07-25）明确写：**"brain 当前实际为锡哥手动生成配置（无后端 / 无定时任务）"；"水印『今日 AI 更新』是戏称，非真定时 AI；M3 才接自动化"**；`禁忌词清单`维护机制写明 M0=锡哥人工审核、M1=brain 自动审核+抽样、M3+=全自动+异常上报；`api-spec` 把 feedback.ts/track.ts 标 **M1**、trend.ts 标 **M2**。
>
> 也就是说，**审核台 / 管理平台 / 反馈回传 / 自我进化 cron / 风险规则衍生层，全部是"自动化时代（M3+）"的能力**。而 BRAIN-PLAN 把这些写成"MVP 前期人工协助调试、后期全自动"的"MVP/Phase 3"系统，**其"MVP"≈ 总纲的 M3**。
>
> **后果**：若 design/eng 双评审 PASS 这份基线、engineering-lead 按"Phase 3=M1 动代码"去建审核台/管理平台/cron，就会与总纲"M0-M2 手动、M3 才自动化"冲突，造成范围误判与主理人期望错位。
>
> **必须做的声明**：BRAIN-PLAN 应在开头显式写——**"本锁闸基线描述的是『自动化终态大脑（≈总纲 M3+）』的设计；M0-M2 阶段大脑=主理人手动配置（无后端/cron/审核台/反馈回传），审核台与自我进化闭环不在此阶段交付。"** 这不是推翻方案，是消除术语歧义。

## 3. 多 app 协同设计一致性（通用底料 + 各 app 调料）

### 3.1 责任归属（⑦）与既有架构一致

⑦ 选 A（大脑统一产多版本 + 派发，app 零加工）**与 api-spec 完全对齐**：api-spec 的 `brain-generator` 已是"1 次 LLM 调用 → `soul_layer` → waimai/mart 各适配 → 签名 JSON"，且明确"一次 LLM 调用同时服务多产品，成本摊薄"。所以"大脑产多版本、app 不加工"在技术上已有落地雏形，不是空想。✅

### 3.2 风格模板机制：多 app 下的冲突 / 重复劳动风险

**风险可控，但有 2 个未设计点**：

1. **风格模板的"责任"清晰，"治理"空白**。初期主理人配种子模板、后期 AI 学腔调（⑦同 A→B 逻辑）——方向对。但 BRAIN-PLAN ⑧.3 P2 仅列"多 app 调料版本管理 + 知识库跨 app 去重（长期治理）"，**没有定义初始治理机制**。当 waimai（胡闹外卖腔）与 mart（反骨导购腔）共享"通用底料"时，若某条新闻被两套模板各产一条高度相似的段子，会出现**跨 app 重复/撞梗**，且大脑"一次调用服务多产品"的成本摊薄假设在"去重"上缺位。

> 🟡 **设计建议 D5（多 app 去重需设计进公式/派发层）**：在派发层增加"跨 app 相似度去重"或"底料复用但调料必不同"的硬约束——例如同一新闻触发时，各 app 段子必须在 `调料维度`（腔调/视角/梗类型）上差异化，否则视为未完成派发。这把"一处写两处受益"从"省事"升级为"不撞梗"。

2. **风格模板=腔调，还是=动机契合？** BRAIN-PLAN 把"调料"窄化为"腔调/语气/梗风格"。从玩家心理看，waimai 玩家偏 **Socializer（截图分享/图鉴）**、mart 玩家偏 **Achiever/Explorer（博弈胜利/反骨）**。风格模板若只调"腔调"而忽略"动机契合"，段子会"像那个 app 的味"但未必"喂到那个 app 玩家的痒点"。

> 🟢 **设计建议 D6（调料含动机维度）**：风格模板除腔调外，显式带一个 `动机契合标签`（如 waimai=social-share，mart=achieve-win），让"胡闹内核"针对不同 app 玩家的 Bartle 类型做定向偏移。成本极低（只是模板多一个字段），但让"多 app 协同"从"同料换皮"升级为"同料定向"。

## 4. 用户体验与产品铁律对齐

### 4.1 纯点击原则：scope 必须澄清（避免假冲突）

"纯点击"铁律针对的是 **app 玩家**（4 痛点滤网的受众，不让玩家输入一个字）。**管理平台的配置（风格模板、RSS 源、权重调参）是主理人操作台，主理人用文本配置是 operator authoring，不是 player input，不违反铁律。**

BRAIN-PLAN ⑧.3 P2 写"纯点击铁律确认：公式参数槽不含用户自由输入"——这句话容易让 engineering 误读成"主理人配置台也不能打字"，进而把主理人该有的轻量配置体验做残。

> 🟢 **设计澄清 D7（纯点击 scope）**：明确"纯点击"约束对象是 **app 端玩家**；公式参数槽由 AI 从新闻/知识库填充，**永不由玩家或主理人自由键入**；但主理人配置台（种子模板、RSS、权重）允许文本输入，这是 operator 工具，不冲突。建议 BRAIN-PLAN 把"用户自由输入"改为"玩家自由输入"以消歧。

### 4.2 轻量后台 / 纯点击管理台

BRAIN-PLAN 的"管理平台 MVP = 看段子/发布/反馈；高危拍板"符合"轻量后台主理人只看结果和拍高危"。审核台"点通过/驳回"是纯点击 ✅。但"调权重/管新闻渠道"若做成复杂表单，会违背"轻量"。建议管理台所有动作收敛为**列表+开关+点选**，权重/渠道用预设档位而非自由填值（呼应 D7 的"主理人可配置但不必自由键入长文本"）。

### 4.3 段子生产是否服务"真实外壳×胡闹内核 / 截图传播"

- **真实外壳×胡闹内核**：方向对（真实新闻+套公式），但如 D1 所述，"反差"未工程化为公式参数，目前靠 LLM 涌现。⚠️
- **截图传播**：如 D2 所述，是目标未度量，且 MVP 因④豁免无闭环信号。⚠️
- BRAND.md §14 的"截图金句库 / 戏精弹层随机抽台词"是 app 端承接，大脑产出的段子需天然带"可截图金句"属性——这应写进③权重的"梗性/传播力"维度，而非只靠 app 端字体设计兜底。

> 🟡 **设计建议 D8（质量>数量须有 Phase 3 机制兜底"安全但无聊"）**：BRAIN-PLAN ⑧.3 P1 已认"安全但无聊"失败模式防御需 Phase 3 机制。我补一条设计侧判据：**当某公式的"红线安全率↑"但"梗性/传播力↓"时，触发"安全但无聊"告警**，强制该公式进入人工复审或降权——把铁律"质量>数量"变成可执行的自动化护栏，而非只靠主理人肉眼发现。

### 🟡 P1（采纳三司会审 + 本评审补充）
- **B1 · 显式声明④豁免的连锁影响**（三司 P1-3，BRAIN-PLAN ⑧.3 已认）：MVP 审核台降级 = 段子+来源链路+基础风险标注（含禁忌词红绿灯等级+误杀/漏掉风险）+上下文；要素 4 以"公式历史通过率+素材红线等级"临时顶替；预埋发布后撤回能力位（D3）。
- **B2 · 反差喜剧工程化（D1）**：公式参数槽内置 `现实锚点 / 胡闹偏移 / 反差强度`，使"真实×胡闹"成为可设计参数而非 LLM 运气。
- **B3 · 截图传播闭环化（D2）**：④反馈回传提为 P1，回传含截图率代理/ replay 率/梗性命中；喂给③"传播力"维度。明确"MVP 大脑=静态种子生成器，非自我进化库"。
- **B4 · 安全但无聊护栏（D8）**：当"安全率↑且梗性/传播力↓"触发告警+降权/人工复审，把"质量>数量"变成自动护栏。
- **B5 · 多 app 去重 + 动机契合（D5/D6）**：派发层加"跨 app 相似度去重 / 调料必差异化"硬约束；风格模板带 `动机契合标签`。
- **B6 · 风险规则库基座更正（§2.1）**：⑧.1 把"风险规则库/合规引擎（待建）"改为"红线基座已具（禁忌词清单 v1.0），待补衍生风险归因层"，避免低估已有资产、也避免 engineering 重复造轮子。
- **B7 · 数据契约基座更正（§2/⑧.1）**：⑤"数据契约（豁免）"实际已有 api-spec v2.2（envelope 6 字段 + L1-L4 降级 + 审核落盘 + 分发层）。BRAIN-PLAN 应显式引用 api-spec 而非当空白；"豁免"仅指 brain 成品段子库的 JSON schema 与 api-spec envelope 的最终对齐，留 Phase 3 细化（非从零设计）。

### 🟢 P2（可留 Phase 3 或后续）
- **B8 · 纯点击 scope 澄清（D7）**：把"用户自由输入"改为"玩家自由输入"，区分 app 玩家与主理人配置台。
- **B9 · 发布后撤回能力位**：MVP 即预埋接口（防旧版变质，⑧.2 前提 4）。
- **B10 · 多 app 调料版本管理 + 知识库跨 app 去重**长期治理（⑧.3 P2）。
- **B11 · RAG 阈值标"待校准" + 监控 cron 归属明确**（三司 P1-4，BRAIN-PLAN ⑧.3 已认）。

## 7. 人话版结论（给产品主理人）

**一句话**：这份大脑设计方案"想得对、方向稳"，可以进开发评审，但**有两件事必须先说清楚，否则开发会跑偏**：

1. **别把"未来全自动大脑"当成"现在就要做的 MVP"**。你现在（M0-M2）其实是**手动配内容**，大脑还没后端、没定时任务、没审核台——这些是全自动阶段（M3+）才有的。方案文档把这些"未来能力"写成了"MVP"，容易让开发哥以为现在就要做审核台和管理后台。先在文档开头加一句话点明"这是终态设计、现阶段手动"，就解开这个误会。

2. **"真实新闻变胡闹段子"和"用户会截图发圈"这两个卖点，现在只是愿望，还没变成可考核的标准**。方案里"反差喜剧"靠 AI 碰运气、"截图传播"连个度量都没有。建议在公式里直接加一个"反差强度"参数，并把"截图率"当成段子好坏的硬指标收回来——这样"质量>数量"才不是空话。

**另外有两个好消息**：你早就有的`禁忌词清单`（红线词库）其实就是审核台"风险标注"的地基，不用从零造；你和 waimai/mart 的"一次产出多版本"接口规范（api-spec）也早写好了。所以审核台和数据格式**不是白纸**，只是还差"新闻衍生风险的归因层"和"跨 app 去重"两小块。

**风险点**：因为"用户反馈回传"被暂缓，现阶段大脑是**不会自我进化的静态生成器**——这点要心里有数，别期待它自己越写越懂你，那得等反馈通道建好。

**综合判断**：🟡 **CONCERNS（有条件通过）**——方案骨架扎实、可逆、无硬伤；补齐上面"阶段声明 + 反差参数 + 截图度量"三件低成本动作后，即可放心双评审进开发。**不判 FAIL**（没到推倒重来的程度），也**不判 PASS**（直接交开发会范围歧义）。
