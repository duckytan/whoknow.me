## 1. 当前架构形态评估（从决策推导出的技术轮廓）

基于 BRAIN-PLAN 的已拍板决策，推导出如下技术架构。它是对"大脑 = 拆解→组装→派发中心 + 管理平台 + 自我进化知识库，只供弹药不上台"的工程落地推演。

### 1.1 系统分层与数据流

```
┌──────────────────────────────────────────────────────────────────────┐
│                         👤 用户层（各 app：waimai/mart/未来）           │
│   纯拉取已部署成品，零风格化加工，运行时绝不依赖大脑在线                   │
└──────────────────────────────────────────────────────────────────────┘
                                   ↓ HTTPS GET（按版本拉，校验失败用旧版）
┌──────────────────────────────────────────────────────────────────────┐
│              🌐 边缘/成品层（Vercel，只读、公开、不可变版本）             │
│   成品段子库 = 各 app 专属 JSON（通用底料+各 app 调料已由大脑套好）        │
│   版本号 + 校验和 + ETag/Last-Modified；一键回退 = Vercel 部署回退         │
└──────────────────────────────────────────────────────────────────────┘
                                   ↑ 推送（brain 生成后部署，原子发布）
┌──────────────────────────────────────────────────────────────────────┐
│                    🧠 大脑（本地/常驻服务器 · 知识产权居留地）            │
│                                                                        │
│  ┌─ 采集层（复用 OpenClaw 7-cron 范式 · M3 自动化）─────────────────┐  │
│  │  信源挖掘/健康检测/快讯采集/流水线加工/深度素材/日报入库/周维度复盘 │  │
│  │  + 合规维度（涉政/涉敏降权或黑名单）                              │  │
│  └───────────────────────────────────────────────────────────────┘  │
│  ┌─ 知识库（热/温/冷分层 + 6维权重升降，归档不删）─────────────────┐  │
│  │  本地存储，不进成品层；含新闻素材 + 学来的优秀段子样本            │  │
│  └───────────────────────────────────────────────────────────────┘  │
│  ┌─ 公式库（每条独立记录 + 版本化 + 只增不删改 + 可解释单元）──────┐  │
│  │  本地存储，AI 只新增不删改；淘汰=标记归档留底                    │  │
│  └───────────────────────────────────────────────────────────────┘  │
│  ┌─ 生成层（拆解→组装→派发）────────────────────────────────────┐  │
│  │  套公式+知识库+新闻+节假日天气 → 产各 app 段子 → 合规审计      │  │
│  │  M0-M2：手动触发，锡哥开 pending 文件批注落盘                   │  │
│  │  M3+：前3级自动发；后2级高危进审核台（你不在时堆积、绝不自动发） │  │
│  └───────────────────────────────────────────────────────────────┘  │
│  ┌─ 管理平台（MVP 最小：看段子/发布/调权重/管新闻渠道/高危拍板）─┐  │
│  │  M0-M2：轻量/手动；M3+：审核台 UI + 代审扩展                   │  │
│  └───────────────────────────────────────────────────────────────┘  │
│  ┌─ 进化层（每日自我进化 cron · M3 自动化）─────────────────────┐  │
│  │  权重重算 + 反馈加权 + 公式淘汰 + RAG 健康度监控（规模触发）   │  │
│  └───────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
                                   ↑ 匿名聚合反馈（④跨环境回传 · M3 自动化）
┌──────────────────────────────────────────────────────────────────────┐
│  反馈回传通道（app→大脑 · M3）：app 端攒本地匿名聚合 → Vercel 收集点 →  │
│  大脑运行时拉取；大脑不在线时排队（时效与兜底设计待 ④ 定）             │

```

**关键区分（评审核心洞察）**：架构必须分清两条路径的可用性边界——
- **服务路径**（app ↔ Vercel 成品库）：只读、不可变、离线容错 ✅。大脑挂了/app 离线，app 用上次成功版本，符合"部署即版本、更新失败沿用旧"。
- **生产/进化路径**（大脑 cron + 反馈回传）：要求大脑在线，**仅在 M3+ 自动化阶段存在**。**大脑关机 ≠ 系统崩**，但**内容会变陈旧 + 进化闭环暂停**。这是设计允许的"诚实降级"，但必须在实现时显式处理（见 1.6 与阻断项 B4）。

### 1.2 存储形态（对应决策 ①公式库、③知识库）

| 资产 | 形态 | 版本化 | 物理删？ | 居留地 | 里程碑 |
|---|---|---|---|---|---|
| **公式库** | 每条独立文件/记录（JSONL 或 `{id}.json`），含 `唯一ID + 版本号 + 创建时间 + 效果评分 + 状态(启用/淘汰/归档) + 来源模范段子 + 生成样例` | 改=出新版本，旧版保留 | 否，淘汰=标记归档 | 本地 | **M0–M2 即可建** |
| **知识库** | 热/温/冷三层目录；每篇文章带 6 维权重分（命中率/时效性/相关性/权威性/稳定性 + 梗性）+ 分层标记 + 保留期 | 权重重算（cron）触发升降层 | 否，冷层归档转存 | 本地 | 存储 M0–M2 建；**升降 cron 属 M3** |
| **成品段子库** | 各 app 独立 JSON（通用底料+各 app 调料已套好），对齐 api-spec v2.2 envelope（见 B1） | 每次生成=新不可变版本 | 不可变快照保留（支持回退） | Vercel（云端，仅成品） | **M0–M2 即可部署** |
| **管理平台数据** | 审核台队列、权重配置、新闻渠道配置、风格模板种子 | 配置版本化 | 按需 | 本地 | 配置 M0–M2；**审核台 UI M3** |

**结论**：全部采用"文件/对象 + 元数据"落地，前期**不引入数据库服务**（契合"花钱原则：前期省"）。这与 OpenClaw 新闻工作流（jsonl 三级池）同构，零试错。

### 1.3 定时编排与多 cron 失败隔离（对应决策 ④新闻子系统复用 OpenClaw + ③升降 cron + 进化 cron · **M3 自动化**）

- **范式**：复用 OpenClaw 已跑通的"7 cron + 三级池 + 5维健康分自动升降级"，每任务独立、单点挂不传染。
- **里程碑定标**：**本能力属 M3 自动化阶段**。M0–M2 大脑为手动触发（api-spec M0 = 手动；禁忌词清单维护机制 M0=锡哥人工、M1=brain 自动审核+抽样、M3+=全自动），**无定时任务**。故 cron 矩阵应"现在设计、M3 才构建"，不应纳入 M0–M2 的 Phase 3 构建范围。
- **大脑 cron 矩阵（M3 设计稿）**：

| 时间 | 任务 | 隔离性 | 关键性 | 备注 |
|---|---|---|---|---|
| 02:00 | 信源挖掘 | 独立 | 高 | 复用 OpenClaw |
| 03:00 | 信源健康检测 | 独立 | 高 | 升降级 |
| 07:00 | 快讯采集 | 独立 | 高 | 原料入库 |
| 07:05 | 流水线加工 | 独立 | 高 | 喂公式 |
| 07:30 | 深度素材 | 独立 | 中 | — |
| 09:00 | 日报入库 | 独立 | 中 | — |
| 周日 20:00 | 周维度复盘 | 独立 | 中 | 反哺策略 |
| 每日 N 点 | **知识库权重重算/升降层** | 独立 | 中 | ③ 实现前置（M3） |
| 每日 N 点 | **每日自我进化**（反馈加权+公式淘汰+RAG健康度监控） | 独立 | 中 | 依赖 ④⑤（M3） |

- **失败隔离原则**：任一 cron 异常只影响该任务，不阻断其他；结果写入独立文件，不跨任务共享可变状态。

### 1.4 部署与回退（对应决策 部署即版本 + Vercel 回退）

- 每次大脑生成 → 产出**新不可变版本**的成品段子库 JSON（带 `version` + `checksum`）。
- 通过 Vercel 原子部署发布（Vercel 每次部署=独立 immutable URL，天然支持一键回退）。
- app 按版本拉取；拉取时校验 `checksum`，失败/缺失则用上一成功版本（对齐 api-spec v2.1 的 `fallback_url` 四级降级 + v2.2 的 L1–L4 降级）。
- 大脑生成失败 → **不发布**，app 继续用上次成功版本（"更新失败沿用旧"）。
- **里程碑**：手动生成→手动部署（M0–M2）与 cron 生成→自动部署（M3）共用同一套 deploy/回退机制，**ADR-003 机制本身 M0–M2 即可落地**。

### 1.5 跨环境数据通道（对应决策 知识产权留本地 + 成品上云 + ⑤数据契约）

- **推模型（push）**：大脑在本地加工（知识产权不出），成品段子库推到 Vercel 给 app 拉取。app 永远只读云端成品，不直接碰知识库/公式库。
- **一致性**：版本号 + 校验和 + 部署清单（manifest）；app 轮询时对比版本，不匹配则维持旧版。
- **数据契约（⑤）非空白**：api-spec v2.2 已定义成品 envelope（version/generated_at/effective_until + meta/food/mart/soul_layer/ui_meta/story_assets/forbidden_check/fallback），含 L1–L4 降级、永远页脚水印、审核落盘（pending→批注→latest-config.json→fetch）、分发层（版本号/ETag）。brain 成品段子库 JSON schema **直接映射该 envelope**（扩成多 app 通用结构），**不从零设计**（见 B1）。

### 1.6 反馈回传与进化闭环（对应决策 ⑤ + ②同类历史 + 进化 cron · **M3 自动化**）

- app 端攒**本地匿名聚合统计**（不持玩家个人数据），定时批量上报大脑侧轻量接收端；大脑不在线时排队。
- 该通道是 ②审核台"同类历史"要素 + "每日自我进化"闭环的**前置**——未建则两者悬空（BRAIN-PLAN 8.3 已声明 MVP 连锁降级）。
- **里程碑定标（v1.1 修正）**：**反馈回传闭环属 M3 自动化**。M0–M2 无后端/cron/反馈回传（总纲 v3 + 禁忌词清单一致）。故 ④ 的"最小形态"应作为 M3 设计项，**不强行塞进 M0–M2 的 Phase 3 构建**；若 Phase 3 确映射到 M3，则 B2 为首批。
- **架构缺口（本文贡献）**：若大脑跑在锡哥本地 PC（可能长期关机、且在 NAT 后），app（Vercel 公网）**无法直接 POST 给大脑**。④须设计为"app 先把匿名反馈发到 Vercel 侧一个无状态收集点（serverless/KV），大脑运行时来拉取"——而非 app 直连大脑。

### 1.7 检索与监控 cron（对应决策 ③-附 RAG）

- 前期知识库小：**权重+冷热层作过滤器挑 Top-N 整批塞 prompt**，不上 RAG。
- RAG 由"检索健康度监控"cron 每日量 7 个触发条件（体量/上下文溢出/成本/延迟/相关性质量/人工干预率/多主题并发），任一达成即提醒用户启动构建。
- 监控 cron 框架可 Phase 3 预埋（每日量阈值），**激活留后期规模触发**；该 cron 本身属 M3 自动化。

### 1.8 阶段映射与总纲里程碑对齐（v1.1 · 关键协调项）

> 本节为吸收 design 双评审（D4/B0，P0）后的**定标透镜**：在动代码前，必须明确 "Phase 3 动代码" 映射到总纲哪个 M，否则架构构建范围会与锡哥的里程碑地图打架。

**总纲 v3 + 禁忌词清单 + api-spec 一致写明**：

| 阶段 | 大脑形态 | 有无后端/cron | 审核台 | 反馈回传 | 自我进化 |
|---|---|---|---|---|---|
| **M0–M2** | 锡哥**手动**生成配置 | ❌ 无 | ❌（锡哥开 pending 文件批注落盘） | ❌（M1 仅简单 👍/👎 POST，非闭环） | ❌ 暂停 |
| **M3+** | **自动化**大脑 | ✅ cron 定时 | ✅ 审核台 UI | ✅ 匿名聚合闭环 | ✅ 每日进化 |

**BRAIN-PLAN 的"MVP/Phase 3"≈ 总纲 M3（自动化终态）**。因此：

- 若 "Phase 3 动代码" = M0–M2（手动）：构建范围 = **ADR-001 存储 + ADR-003 手动 deploy/回退 + ⑤对齐 api-spec + 手动审核流程（锡哥开文件批注，无 UI/cron）**。NOT cron、NOT 审核台 UI、NOT 反馈回传自动化。
- 若 "Phase 3 动代码" = M3（自动化）：构建范围扩展 = ADR-002 cron + ADR-004 反馈回传 + 审核台 UI + 进化闭环。

**本评审要求**：BRAIN-PLAN 开头须显式声明阶段映射（design-lead B0 负责补）；本 ADR 中 **ADR-001/003 与 ⑤对齐 适用于 M0–M2 可直接构建**，**ADR-002/004 与审核台 UI/进化闭环属 M3 自动化，须待映射明确后再定是否纳入 Phase 3 构建**。这样既不阻塞开工，又避免"现在就建审核台+管理后台+cron"的范围误判。

## 2. 关键 ADR（基础层决策）

> 每条 ADR 锁定在 BRAIN-PLAN 已拍板方向上，不引入新业务决策；作用是为 Phase 3 提供可执行的工程约束，并按里程碑标注构建时机。

### ADR-001 · 存储选型（公式库 / 知识库的落地形态与版本化）· **M0–M2 可构建**

- **背景**：①公式库需"独立记录+版本化+只增不删改+可解释+回退"；③知识库需"热温冷分层+权重升降+归档不删"。二者都要求前期省、不引入数据库服务。
- **选项对比**：
  | 方案 | 说明 | 优 | 缺 |
  |---|---|---|---|
  | **A 文件/对象 + 元数据**（选定） | 公式=独立 JSON/JSONL；知识库=分层目录 + 每篇元数据文件 | 前期零服务成本、天然版本化（写新不覆盖）、离线可用、与 OpenClaw jsonl 同构 | 跨文件查询需自管索引；并发追加需文件锁；规模到 ~1万 条需升级 |
  | B 单文件大表 | 一个 JSON 存全部 | 简单 | 并发冲突/误改脆点（BRAIN-PLAN 已否）、难回退 |
  | C SQLite | 本地库 | 查询强 | 前期过重（花钱原则否）、单人友好期过度设计 |
- **决定**：采用 **A**。公式库每条独立文件（`formulas/{id}.json` 含版本数组或 `formulas/{id}@{version}.json`）；知识库按 `hot/ warm/ cold/` 分层目录，每篇 `article.json` 带 6 维权重 + 分层标记 + 保留期。
- **选定理由**：完美支持"只增不删改、回退、归档"，对接资产安全与合规审计；避开大表并发脆点；复用已验证文件范式；延迟"该买服务器"触发点。
- **风险**：
  1. 全库重算（权重升降、公式淘汰）需遍历文件 → 前期量小可接受，到 RAG 触发条件（~1万条）时须迁移到 DB/RAG（已在 ③-附 规划）。**权重升降 cron 属 M3，不影响 M0–M2 存储构建。**
  2. 追加竞争：生成与审核/权重 cron 同时写同一文件需文件锁或串行化（M3 才涉及）。
  3. **缓解**：元数据索引文件（`index.json` 记录 ID→路径+状态+权重）加速查询；写操作统一走一个 writer 模块。

### ADR-002 · 定时编排与多 cron 失败隔离 · **M3 自动化（现在设计，M3 构建）**

- **背景**：新闻子系统复用 OpenClaw 7-cron；另需权重升降 cron、进化 cron、RAG 监控 cron。大脑"非永远在线"，须保证单点故障不传染、且关机不崩服务。
- **选项对比**：
  | 方案 | 说明 | 优 | 缺 |
  |---|---|---|---|
  | **A 多独立 cron（选定）** | 每任务一个独立 cron，独立文件输出 | 单点挂不传染、复用 OpenClaw 范式、轻量免费 | cron 数量管理散（OpenClaw 有 3 个 P2 闲置脚本坑） |
  | B 单体夜跑脚本 | 一个脚本跑全流程 | 易管理 | 一处挂全崩，违背隔离 |
  | C 常驻调度器/编排 | 专用服务 | 可视化强 | 前期过重、花钱原则否 |
- **决定**：采用 **A**，并补充两条工程约束：(1) **cron 注册表**——所有 cron 集中登记（名称/时间/输出文件/依赖/关键性），避免 OpenClaw 式"脚本写完没排 cron"的闲置坑；(2) **运行环境决策**——明确大脑跑在常驻轻量服务器 vs 锡哥本地 PC；若本地 PC，**cron 仅在开机时跑**，且服务路径（app 拉 Vercel）不受影响，仅生产/进化暂停（诚实降级）。
- **里程碑**：本 ADR 描述的能力 **M3 才构建**。M0–M2 大脑手动触发，无 cron；故 ADR-002 是"设计交付"，非 M0–M2 Phase 3 构建项。
- **选定理由**：契合"前期轻量 cron、后期该买常驻服务器就买"；隔离失败；零试错。
- **风险**：
  1. 本地 PC 关机 → 采集/权重/进化全部暂停，内容陈旧（非崩溃，但需产品主理人知晓）。
  2. cron 散落难维护（OpenClaw 实证坑）→ 用注册表 + 单一 `daily-run.sh` 入口编排缓解。
  3. **缓解**：关键 cron（采集/加工）失败须有告警（复用 api-spec `brain_uptime`/`last_generated_age_hours` 监控）。

### ADR-003 · 部署与回退机制（Vercel 部署回退 ↔ "更新失败沿用旧"）· **M0–M2 可构建**

- **背景**：部署即版本；更新失败 app 用上次成功数据；大脑挂了不影响已部署 app；Vercel 部署回退更合适。
- **选项对比**：
  | 方案 | 说明 | 优 | 缺 |
  |---|---|---|---|
  | **A Vercel 不可变部署 + 一键回退（选定）** | 每次生成=新 immutable 部署，带 version+checksum；回退=Vercel 部署回退 | 原子发布、天然回退、对齐 api-spec CDN 层 | 回退是部署级非内容级；需 checksum 兜底 |
  | B 自托管版本化静态 | 自己管版本目录 | 可控 | 需自建回退逻辑 |
  | C CDN 版本化路径 | 路径带版本 | 可并存多版 | 旧版堆积需清理 |
- **决定**：采用 **A** + 内容级校验。大脑生成成品 JSON → 写本地 → 推 Vercel（新部署）→ 写 `manifest.json`（当前 version + checksum）。app 拉取时：(1) 读 manifest 拿版本；(2) 校验内容 checksum；(3) 失败/缺失则用缓存的上次成功版本。生成失败**不触发部署**。手动生成（M0–M2）与 cron 生成（M3）共用此机制。
- **选定理由**：与 api-spec v2.1（Cloudflare/Vercel + version + ETag + fallback_url 四级降级）及 v2.2（L1–L4 降级）天然对齐；质量>数量铁律落地为"宁用旧版不用坏版"。
- **风险**：
  1. **"旧版≠安全"（BRAIN-PLAN 8.2-4）**：降级用的旧版本身可能已变质（含违规/bug）。→ 须有**撤回/失效清单**（revocation list）：某 version 被发现违规，标记失效，app 跳过该版回退到更前的安全版。Phase 3 预埋接口（见阻断项 S2）。
  2. 部署与 app 看到之间存在时间窗 → 用 manifest 原子更新 + app 版本比对缓解。

### ADR-004 · 跨环境数据通道（本地大脑 → Vercel 成品库 → app 拉取 的安全与一致性）· **M3 自动化（反馈回传侧）**

- **背景**：知识产权留本地不出；成品段子库上云给 app 拉；app 与大脑反馈跨环境回传（④）。
- **选项对比**：
  | 方案 | 说明 | 优 | 缺 |
  |---|---|---|---|
  | **A 推模型 + 云端反馈收集点（选定）** | 大脑推成品到 Vercel（只读公网）；反馈走 Vercel 侧 serverless 收集点，大脑拉取 | IP 边界干净、app 永不直接碰知识库、大脑离线容错 | 需 ④ 反馈收集点设计（M3） |
  | B app 直连大脑 | app POST 大脑 | 简单 | 大脑在 NAT/关机时不可达，不可行 |
  | C 中间同步服务 | 独立同步层 | 解耦 | 前期过重 |
- **决定**：采用 **A**。
  - **下行（大脑→app · M0–M2 即可）**：大脑本地加工 → 推 Vercel 成品库（只读、公网、不可变版本）。IP 居留地=本地（知识库/公式库/加工方法永不上云）。
  - **上行（app→大脑 · M3）**：app 端攒本地匿名聚合 → POST 到 **Vercel 侧无状态反馈收集点**（serverless function + KV/对象存储，仅存匿名聚合，不持个人数据）→ 大脑运行时拉取归并本地。大脑不在线时反馈在云端排队，不丢。
  - **安全**：成品库公网只读、无需鉴权（api-spec M0）；反馈收集点须鉴权（api-spec M1 Bearer / M3 HMAC 防刷）；大脑拉取反馈用服务端密钥。
- **里程碑**：下行（推成品）M0–M2 即可；**上行（反馈回传）属 M3 自动化**，须待 ④ 映射明确后构建。
- **选定理由**：干净隔离 IP 边界；app 纯消费端、运行时零依赖大脑；解决"大脑在 NAT/关机时 app 无法直连回传"的实际阻塞。
- **风险**：
  1. ④ 反馈收集点 = 新增公网组件，须做匿名聚合（不持个人数据）+ 防刷（频率限制/签名）。
  2. 上行延迟：反馈可能滞后到大脑下次运行才归并 → 进化闭环有"T+1"延迟，MVP 可接受，须声明。

### （附）ADR-005 · 检索策略与 RAG 触发（前期不建，框架预埋）· **M3 监控 / 后期激活**

- **背景**：③-附 RAG 定为后期计划，由 7 条件客观触发。
- **决定**：前期用"权重+冷热层过滤挑 Top-N 整批塞 prompt"；**Phase 3 预埋"检索健康度监控"cron 框架**（每日量 7 条件，阈值标"待校准"），激活留规模触发；权重如何进检索（先过滤 or 重排）、冷层是否可搜，由实际引入时的检索架构 ADR 定（BRAIN-PLAN 已注明）。
- **理由**：避免前期过度构建；监控自动化保证"触发即提醒"（铁律）。监控 cron 属 M3 自动化。

## 4. 阻断项清单（进 Phase 3 动代码前必解 / 必声明）

> 分三类：**B 类 = 必须在写业务代码前落实的契约/声明**；**S 类 = 必须在实现契约中显式声明的范围/机制**（不阻塞开工，但不写清会重蹈"太顺了"妄执）。**里程碑标记**：🔷 M0–M2 即建 / 🔶 M3 自动化。

### B 类（契约级前置 · 不解决则代码对不上或范围打错）

- **B0 · 阶段映射声明（P0 协调项 · design-lead B0/D4）** 🔷需先声明
  - 内容：BRAIN-PLAN 开头显式写——"本锁闸基线描述自动化终态大脑（≈总纲 M3+）；M0–M2 = 主理人手动配置（无后端/cron/审核台/反馈回传），审核台与自我进化闭环不在此阶段交付。"
  - 现状：design-lead 负责在 BRAIN-PLAN 补；**本架构评审的 Phase 3 构建范围依赖此声明**。
  - 阻塞等级：🔴 P0 协调（不声明则 ADR-002/004/审核台/进化会被误排进 M0–M2 构建，与总纲里程碑打架）。

- **B1 · ⑤ 数据契约对齐 api-spec（非从零设计 · design-lead B7）** 🔷 M0–M2 即建
  - 内容：brain 成品段子库 JSON schema **直接映射 api-spec v2.2 envelope**（version/generated_at/effective_until + meta/food/mart/soul_layer/ui_meta/story_assets/forbidden_check/fallback），扩成多 app 通用结构；复用 L1–L4 降级、永远页脚水印、审核落盘（pending→批注→latest-config.json→fetch）、分发层（版本号/ETag）。

  - 阻塞等级：🟡 中（不开工则 app/brain 无法联调；但非白纸，对齐即可）。

- **B2 · ④ 反馈回传最小形态（M3 自动化 · design-lead D2/B3 提为 P1）** 🔶 M3
  - 内容：app 端匿名聚合格式 + Vercel 侧反馈收集点（serverless+KV）+ 大脑拉取归并协议 + 排队/时效/兜底。
  - 现状：豁免留 Phase 3；但它是 ②"同类历史" + 进化闭环的前置。**里程碑定标后明确：属 M3 自动化**，若 "Phase 3 = M0–M2" 则不纳入 M0–M2 构建；若 "Phase 3 = M3" 则为首批。
  - 解法：采用 ADR-004 的"云端反馈收集点"形态。MVP/M0–M2 可只落"app 攒批 + 收集点存匿名聚合 + 大脑拉取落本地文件"最小版，不要求完整进化算法。
  - 阻塞等级：🟡 中（视 Phase 3↔M 映射；M0–M2 下不阻塞开工，但须在设计稿中预留）。

### S 类（实现契约须显式声明 · 防"机制=已解决"妄执）

- **S1 · ② 审核台 MVP 降级范围 + 红线基座已具（design-lead B1/B6/D3）** 🔷 M0–M2 手动 / 🔶 M3 UI
  - 红线基座已具：禁忌词清单 v1.0（红绿灯分级 + 误杀率10%/漏掉率0.1% + M0–M3 维护机制）**就是 风险规则库/合规引擎 的红线子集基座**，且 api-spec `generator/forbidden.ts` 已实现 3 级红绿灯过滤。故 ②"基础风险标注"**现在即可建**，仅待补"新闻衍生风险归因层"（衍生自哪条涉敏新闻）。
  - 声明：M0–M2 审核 = 锡哥开 pending 文件批注落盘（api-spec P0-2），无 UI；M3 审核台 UI = 段子 + 来源链路 + 基础风险标注（禁忌词红绿灯等级 + 命中误杀/漏掉风险）+ 上下文；要素 4（同类历史，依赖 B2④）以"公式历史通过率 + 素材红线等级"**临时顶替**（design-lead D3 替代判据），并预埋发布后撤回能力位。**明确不含**"全量实时合规扫描"（待补衍生层）。
  - 利好：三司把"合规引擎待建"列 ② 隐藏依赖、判 FAIL；经 design + eng 双评审确认红线基座已具 → ② 从 FAIL 降级为"MVP 可落地+增强待建"。

- **S2 · "旧版≠安全"——撤回/失效清单必须 Phase 3 预埋接口（BRAIN-PLAN 8.2-4）** 🔷 M0–M2 即预埋
  - 对应 8.2-4。降级用的旧版可能含违规/bug。
  - 声明：成品库须支持"version 失效标记"（revocation list），app 回退时跳过失效版。接口 Phase 3 预埋，触发逻辑随合规事件填。

- **S3 · "安全但无聊"失败模式防御必须 Phase 3 落地质量>数量机制（design-lead D8/B4）** 🔷 M0–M2 即预埋信号
  - 对应 BRAIN-PLAN 8.3 P1 + design D8。质量加权须含"梗性/传播力"维度；当"红线安全率↑且梗性/传播力↓"触发"安全但无聊"告警 + 降权/人工复审，把铁律变自动护栏。
  - 声明：进化 cron（M3）的打分与公式淘汰，必须以"梗性+反馈表现"为正向信号；M0–M2 先在段子结构预留 `梗性/传播力` 字段与告警判据位。

- **S4 · 大脑运行环境必须明确（本文新增）** 🔷需决策
  - 影响：cron 可靠性（ADR-002）、反馈回传时效（ADR-004 上行）、进化闭环连续性。
  - 建议：MVP/M0–M2 可跑锡哥本地 PC（手动触发）；但若要做到"每日自动进化 + 反馈不积压"，应尽早上一台常驻轻量服务器（契合"后期该买就买"）。此决策不阻塞开工，但须在 Phase 3 计划中标明，避免 cron 依赖假设落空。

## 6. 人话版结论（给产品主理人看）

> 一句话：**这份大脑的设计蓝图方向是对的、能盖楼，但开工前必须先把"现在到底是手动阶段还是自动阶段""app 和大脑拉数据的格式（其实早就有规范了对齐即可）""用户反馈怎么回传（那是后期自动阶段才做的事）"三件事说清，否则开发会跑偏或两边对不上。**

1. **蓝图本身没问题**：大脑怎么"抓新闻→学段子→归纳公式→产段子→派给各 app"、怎么"挂了也不影响已上线的 app"、怎么"知识产权留家里只把成品送上云"——这些大方向都拍板清楚了，也跟已有的技术规范（api-spec）对得上，没有"致命硬伤"。

2. **最关键的一条：别把"未来全自动大脑"当成"现在就要做的 MVP"**。你现在（M0–M2 阶段）其实是**手动配内容**——大脑还没后端、没定时任务、没审核台，这些是全自动阶段（M3+）才有的。方案文档把这些"未来能力"写成了"MVP"，容易让开发哥以为现在就要做审核台和管理后台。**先在文档开头加一句话点明"这是终态设计、现阶段手动"，就解开这个误会**（design 双评审已把这个列为最高优先级协调项）。

3. **两条"接口协议"要尽早定，但都不是白纸**：
   - **数据格式（⑤）**：app 和大脑之间拉数据的格式，**api-spec 早就写好了**（一套标准的成品 JSON 结构 + 降级规则 + 水印），只要把大脑产出的段子库对齐这份规范就行，**不用从零设计**。
   - **反馈回传（④）**：用户反馈怎么回传大脑，是**后期自动阶段（M3）**才自动化做的事；现阶段手动，不强求。但它的"最小样子"得先设计好，免得后期返工。

4. **审核台可以先"简配上线"**：之前担心"人工审核台要显示5种辅助信息，缺好几个零件做不出来"。但我们发现：你早就有的`禁忌词清单`（红线词库+红绿灯分级）其实就是审核台"风险标注"的地基，加上现有的禁忌词过滤器，**基础风险标注现在就能做**；只差"新闻衍生风险的归因层"一小块。所以 MVP 先做"段子+来源+基础风险标注+临时替代判据"，完全能上线。

5. **两个要提前防的坑**（设计里已意识到，本文要求实现时写进代码）：
   - **"旧版本不一定安全"**：降级用的老段子库万一某天被发现违规，得能一键"拉黑"那个旧版，不能傻傻回退到问题版本。
   - **"安全但无聊"**：为了不犯错而把段子改得不好笑，就违背了"胡闹"的初心。质量的打分必须包含"够不够好笑/够不够能传播"，且当"越安全越不好笑"时要自动报警。

6. **一句话收尾**：设计锁闸可以收口、架构评审**条件性通过**——只要 Phase 3 开工先把"阶段映射声明"补上、把数据格式对齐 api-spec、并把上面两个坑的预防写进实现，就能放心写代码。审核台 UI、定时任务、反馈回传闭环、RAG 这些重活，**确认 Phase 3 对应到自动阶段（M3）才建，否则留到后期**。

## 附录 A · 与 api-spec v2.1/v2.2 的对齐确认

- **拓扑一致**：api-spec 的 `brain-generator → brain-deployer → Cloudflare R2/S3/Vercel` + `version + ETag + Last-Modified + fallback_url` 四级降级，与本文 ADR-003/004 完全对齐。BRAIN-PLAN 的"成品段子库部署 Vercel"是 api-spec 云分发层的具象化。
- **数据契约基座已具（B1/B7）**：api-spec v2.2 已定义成品 envelope（6 字段 + L1–L4 降级 + 永远页脚水印 + 审核落盘 pending→批注→latest-config.json→fetch）+ 分发层（版本号/ETag）+ 生成层（LLM→禁忌词过滤→签名 JSON）。brain 成品段子库 JSON schema **直接映射该 envelope**，不从零设计。
- **合规基座已存在（S1/B6）**：api-spec `generator/forbidden.ts`（禁忌词 3 级红绿灯）+ `docs/禁忌词清单-v1.0.md`（红绿灯 + 误杀率10%/漏掉率0.1% + M0–M3 维护机制）已为 M0 必做 → ② 的"基础风险标注"有现成引擎，仅"新闻衍生风险归因层"待补。
- **鉴权对齐**：成品库公网只读（M0 不鉴权）；反馈回传（④）走 M1 Bearer / M3 HMAC（防刷、防重放），与 api-spec 鉴权三阶段一致。
- **降级策略一致**：api-spec "质量>数量，宁没新内容也不出错" + 四级降级，与 BRAIN-PLAN "部署即版本、更新失败沿用旧"同构。
- **里程碑一致**：api-spec M0 手动触发/无 cron/审核=手动落盘，M1 加 cdn/soul/news/feedback👍👎，M3 mart+多产品+团队化；与总纲 v3 "M0–M2 手动、M3 自动化"一致。

## 附录 B · 与 OpenClaw 新闻工作流 v1.0 的对齐确认

- **范式复用确认**：7 cron + 三级池（候选/观察/正式）+ 5 维健康分自动升降级 + 周维度闭环，大脑新闻子系统直接复用，零试错。**该 cron 矩阵属 M3 自动化（见 1.3/1.8）。**
- **改造点映射**：
  1. 输出目标：OpenClaw 推人看早报 → 大脑结构化素材入库知识库（喂公式）。✅
  2. 新增"合规性"维度：涉政/涉敏源降权或拉黑（因新闻衍生段子归高危必审）。✅ 对应 ADR-002 健康分加合规维度。
  3. 源类型扩展：加泛娱乐梗源。✅ Phase 3 配源。
  4. 定位：OpenClaw 是终点，大脑新闻获取是上游中转站。✅
