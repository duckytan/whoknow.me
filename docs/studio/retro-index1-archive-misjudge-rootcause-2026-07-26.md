# RETRO · index1.html 归档误判根因分析（2026-07-26）

> 类型：流程缺陷复盘（对应规范 §4「审计/会审」类，命名 `-YYYY-MM-DD`）
> 触发：用户在「归档 index1.html / 对齐 README / 提交 git」环节质疑"为何要归档 index1.html"，回溯发现规范 §8 自相矛盾。
> 结论：不归档；规范 §8 改为"保留（部署源文件不可删）"，§7 新增"部署源文件红线 + 防再犯双闸门"。

## 1. 事件
- 规范 v1 草案（§8 遗留①）曾写"建议归档 `index1.html` 至 `archive/root-obsolete/`"。
- 三司会审后 §2 已改为"允许保留（不强制唯一）"，§8 却残留"建议归档"——**同一规范两处结论相反**。
- 若执行归档：`build-for-vercel.js` 第 31 行 `['index.html','index1.html',...].forEach(copyToDist)` 将因源文件缺失导致部署构建报错。

## 2. 根因链（6 层）
1. **现象**：规范 §8 建议归档 `index1.html`，与 §2 自相矛盾；执行会破坏构建。
2. **§8 为何这么写** → 沿用 v1 草案"现状问题 #3"旧结论（双 HTML 入口被定为"待治理项"，倾向归档）。
3. **#3 为何倾向归档** → 勘察时发现根有 `index.html`+`index1.html`"含义不明"，第一反应"门面不整洁、该清理"，未先查 `index1.html` 工程角色。
4. **为何先入为主当整洁问题** → 起草时带着"根目录只放入口与权威、保持门面级"预设，双入口触发"该清理"直觉（破妄诀所指"洁癖妄执 / 共识妄执"）。
5. **三司纠正 §2 后 §8 为何没同步** → 修订按 P0/P1 逐段改被点名处，把 §8 当"用户待办登记册"原样保留，未意识到与 §2 新结论冲突；缺"全文回扫"。
6. **根因** → ① 框架偏差：**先定性（整洁问题）后/不核查（工程角色）**；② 流程缺陷：**孤立段落编辑 + 缺全文一致性回扫**；③ 规范自我违反"单一事实源"（§2/§8 结论相反）。

## 3. 关于"是否忘记"
- 事实未丢：当日日志明确记着"index1.html 归档待拍板"。
- 但只记了待办、**未深挖"为何会有这个待办"**，故被质疑才暴露它根本不该存在。
- 模式复盘：从 prototype 归档到本次，惯性是"先按整洁/治理直觉移动或归档文件，再被事实打脸"。prototype 那次因动手前做了核查（确认只是参考图）而安全；index1 这次在"建议归档"阶段**未做构建依赖核查**就写进规范。差的那一步就是"先核查"。

## 4. 防再犯机制（已写入规范 §7）
- **闸门一·前置核查**：任何"归档/移动/删除"建议提出前，先 `grep` 仓库（构建脚本/配置/路由/其他文档）确认该文件非部署或运行依赖——未核查不得写入规范或执行。
- **闸门二·修订回扫**：改完某条结论后，立即 `grep` 全文所有提及该对象的位置，逐处对齐结论，杜绝"同一规范两处结论相反"。
- **事实写死**：`index.html` / `index1.html` 在规范 §7 列为"部署源文件红线，必须保留，禁止归档/移动/删除"。

## 5. 元教训
- "单一事实源"不仅是内容原则，也是**规范自洽原则**：同一对象在规范内只允许一处结论。
- 修订他人/旧结论时，被点名的段落改了，必须回扫所有引用处。
- AI 协作的"整洁直觉"需让位于"工程事实核查"——直觉可作假设，不可作结论。
